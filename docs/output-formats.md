# 输出格式实测

本页记录 `dsh-paste-image` 把图片转码成 PNG、JPEG、WebP 时的真实体积与编码耗时：同一批夹具、同一个真实 Chromium、同一段 `normalize()` 代码，逐字节量出来。面向用户的简版结论在 [README 的配置一节](../README.md#配置)，格式判定规则见[格式支持](formats.md)。

结论先说：**体积比例取决于内容，没有一个能当承诺的百分比。** 照片用 JPEG/WebP 能小约 82%，但同一组参数下 UI 截图用 JPEG 反而比 PNG 大 49%；像素画和小图标更适合 PNG 或 WebP，而不是 JPEG。

## 测试环境

| 项目       | 值                                                                       |
| ---------- | ------------------------------------------------------------------------ |
| 浏览器     | Chromium 156.0.8078.4（Playwright 1.65.1 驱动的真实 Chromium，headless） |
| 系统       | Ubuntu 26.04.1                                                           |
| CPU        | Intel Core i7-13700K                                                     |
| 设备像素比 | 1                                                                        |
| 质量参数   | q=0.92（插件默认值），另测一组 q=0.8                                     |
| 编码入口   | `client.js` 的 `normalize()`，与用户实际粘贴时走的是同一段代码           |
| 尺寸上限   | `maxSide` 默认 4096 px；本组夹具都没有触发缩放，输出尺寸与输入一致       |
| 体积换算   | 1 KB = 1000 B（本页所有 KB 均按此换算）                                  |

## 测量方法

1. 夹具在页面里画到 canvas，再用 `canvas.toBlob('image/png')` 取 PNG 字节。
2. 把 PNG 字节包成 `File`，**声明类型写成 `image/bmp`**。这一步是必须的：同样的字节如果声明成 `image/png`，`normalize()` 会判定为原生格式直通、直接返回，根本不会编码；声明成 BMP 才会真正走「解码 → 画布 → 重编码」的路径。解码回来的像素与原始 PNG 完全一致，所以比较的只是输出编码。
3. 每个格式先跑 1 次预热，再计时 9 次取中位数；计时包住 `normalize()` 的整个 `await`。
4. 体积取输出的 `File.size`，类型取 `File.type`，确认没有因为编码器缺失回退到别的格式。
5. 每个夹具另做一次正确性校验：插件输出的 PNG 与直接 `canvas.toBlob('image/png')` 的结果逐字节相同，5 个夹具全部一致。
6. q=0.92 与 q=0.8 各跑一轮；PNG 不传质量参数，所以两组里 PNG 的数值相同。

前四个是合成夹具，用来覆盖内容类型的两端：硬边缘/平坦色块（UI 截图、像素画）与连续色调（照片）；透明 logo 单独覆盖 alpha 通道。第五个是真实文件，用来确认合成夹具的结论在真实素材上同样成立。合成夹具不模拟「某张具体照片」，只模拟内容结构。

## 怎么读这组数字

- **体积比例依赖内容，不是通用常数。** JPEG 在 UI 文字上是 +49%，在照片上是 -82%；把任何一个百分比当成对用户的承诺都会翻车。
- **UI/文字类：PNG 常常就是更小的那个。** 这组里 PNG 69.7 KB，JPEG 103.6 KB；WebP 体积最小（33.9 KB），但编码耗时约 65 ms，是 PNG 的 6 倍左右。
- **照片类：JPEG/WebP 都约 -82%。** q=0.92 下 WebP 只比 JPEG 小约 3%，编码却慢 4.5 倍（224.8 ms vs 49.9 ms）；把质量降到 q=0.8 后 JPEG 反而比 WebP 更小（317.9 KB vs 339.7 KB）。
- **透明：JPEG 没有 alpha。** 透明像素会被合成到白底（表里 `-92.6%` 的代价就是丢了 alpha）；需要透明就选 PNG 或 WebP。这组里 WebP q=0.92 保留 alpha，同时比 PNG 小 84%。
- **像素画：PNG 本来就只有 4.1 KB。** JPEG/WebP 能省约 28%，但两者都是有损编码，硬边缘容易出现振铃/色渗；几百字节的收益换边缘瑕疵通常不划算。
- **小图标：WebP 省 36%，JPEG 反而比 PNG 大 29%。** 图标尺寸小，JPEG 的块效应和头部开销都不占优。
- **正确性校验通过：** 插件输出的 PNG 与直接 `canvas.toBlob('image/png')` 逐字节相同（5/5 夹具），输出尺寸与输入一致（`maxSide` 默认 4096，本组未触发缩放）。

## 这些数字不保证什么

- **合成夹具、单机单浏览器。** 五个夹具覆盖的是内容类型，不是真实世界的全部素材；同一张图换内容、换分辨率、换浏览器版本，比例都会变。
- **耗时只代表这台机器。** Ubuntu 26.04.1 + i7-13700K + Chromium 156、headless、DPR 1；其它机器上 ±10% 属于正常波动。体积是确定性的：同样的输入、编码器和参数会得到同样的字节数。
- **中位数不是上界。** 9 次计时取中位数，冷启动、GC 与系统负载都可能让单次耗时明显高于表里的数字。
- **不构成质量承诺。** 有损编码的视觉质量是主观的；表里的 q=0.92 是插件默认值，不是「对所有图片都合适」的质量。

## 如何复现

仓库里**没有**提交测量脚本：它需要一个真实的 Chromium 和一份 Playwright 安装，不适合塞进零依赖的插件仓库。复现时自己写一个一次性脚本即可：

1. 用 Playwright 启动 headless Chromium（`deviceScaleFactor: 1`），打开一个空白页面。
2. 在页面里准备夹具：canvas 绘制，或加载 `assets/icon-180.png` 后画到 canvas。
3. 把 `client.js` 作为脚本注入页面，用一个最小的 `window.__ModuleLoader__` 桩接住 factory，拿到返回的 `api`。
4. 用 `api.applySettings({ outputFormat, quality })` 设定格式与质量，调用 `api.normalize(file)`；`file` 是 PNG 字节、声明类型为 `image/bmp` 的 `File`。
5. 每个格式先预热 1 次，再计时 9 次取中位数；体积用 `file.size`，类型用 `file.type`。另跑一次 `canvas.toBlob('image/png')` 做逐字节比对。

复现时请固定浏览器版本与 DPR，否则数字之间不可比。插件的编解码实现与设置项见[工作原理 · 13. 设置与配置页](how-it-works.md#13-设置与配置页)，默认值与取值范围见 [README 的配置表](../README.md#配置)。
